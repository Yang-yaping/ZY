# P2P 网络与区块同步模拟实验

作业一的可运行 Python 项目。100 个已有节点与 1 个新节点使用真实的本机 TCP 连接；新节点完成发现、下载、密码学校验与状态提交。网页提供交互演示，命令行批量采集可复核的实验数据。

## 给第一次运行的同学

1. 将整个文件夹解压，保留目录结构。**交作业的源代码是 `app.py`、`lab/`、`tools/` 和 `tests/`，不是终端中显示的登录文字。**
2. 安装 Python 3.11 或 3.12（本次实际验证版本见 `results/metadata.json`）。
3. 在这个文件夹打开终端，逐行输入：

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m streamlit run app.py
```

4. 浏览器打开 `http://127.0.0.1:8502`，点击“开始实验”。Mac 也可尝试双击 `start.command`；首次安装依赖需要联网。
5. 结束演示：回到启动窗口按 `Control+C`。关闭浏览器不会自动停止服务器。

Windows 激活命令为 `.venv\Scripts\activate`，其余命令相同。请勿把 Mac 的 `.venv` 复制到 Windows 使用。如果提示 8502 端口占用，运行 `python -m streamlit run app.py --server.port 8503`，然后打开新端口。

本次已在交付数据记录的 macOS / Python 3.12 环境实际验证，其他平台尚未实测。`python-bitcoinlib` 需要可供 ctypes 加载的 OpenSSL；如果出现 SSL 库加载或符号缺失错误，应先配置与 Python 架构匹配的 OpenSSL，再运行 `python -c "from bitcoin.core.key import CECKey; print('OpenSSL OK')"` 检查。这类依赖问题不应通过跳过真实验签来绕过。

`127.0.0.1` 指各自的电脑。老师要操作网页，需要收到整个项目后运行；本次交付没有自动发布到 GitHub 或公网。

## 重新运行实验

在已激活的虚拟环境中：

```bash
python -m unittest discover -s tests -v
python tools/validate_fixtures.py
python tools/run_experiments.py --repetitions 3 --output results
python tools/analyze.py
```

批量实验会覆盖同名 CSV，建议复测使用 `--output results_rerun`；统计脚本相应使用 `--input results_rerun`。实验需要几分钟，受电脑性能影响。命令行输出到“Completed”才代表整组完成。

默认复用公开夹具，确保两种策略传输完全相同的字节；加 `--fresh` 会使用新私钥重新生成夹具。私钥仅在生成时驻留内存，没有写入项目。固定种子只控制拓扑、场景顺序和非秘密填充内容，**不用于生成私钥或 ECDSA 随机数**。运行时间不会完全相同，比较应采用重复测量的均值与标准差。

## 协议与系统模型

采用 `asyncio` 的 TCP 流。每个节点绑定 `127.0.0.1` 的不同临时端口，属于单机多节点仿真，**不是 100 台物理主机**。节点拥有独立的邻居表与服务容量。公开只读区块在内存中共享以降低单机实验开销；新节点的可服务高度从 0 开始，仅在下载并验证后更新。

TCP 提供可靠、有序的字节流，避免自己实现分片重排与传输确认，适合区块数据下载。但 TCP 没有消息边界，因此控制消息使用 4 字节大端长度前缀和 JSON，限制为 64 KiB；区块数据使用响应头中的长度读取。TCP 不证明数据来源诚实，仍需哈希、签名、UTXO 和可信检查点。

消息有 `HELLO`、`PING`、`HEADERS`、`GET(height, offset)`。新节点仅获知 3 个种子，通过邻居信息扩展并主动验证，下载器从已发现列表中使用同样的 4 个提供者。`GET` 支持断点；不同提供者提供同一不可变区块，最终对完整内容校验，不能仅信任已接收前缀。

同步流程：未加入 → 发现 → 获取与检查头部清单 → 有界下载 → 按高度校验 → 提交 UTXO 状态 → 完成。失败会进入退避与换源，超过 30 次尝试明确失败。单个区块校验先使用 UTXO 副本，全部通过后替换状态；这是单进程内的全有或全无更新，不涉及数据库事务或分布式共识。

## 密码学实现和教学简化

- 交易使用 `python-bitcoinlib` 的真实 Bitcoin 旧式交易序列化、`SignatureHash(..., SIGHASH_ALL)` 与 `VerifyScript` 栈式解释器。不是用布尔函数模拟 `OP_CHECKSIG`。
- 锁定脚本：`OP_DUP OP_HASH160 <公钥哈希> OP_EQUALVERIFY OP_CHECKSIG`。解锁脚本：`<DER签名+01> <压缩公钥>`。
- 公钥为 secp256k1；私钥由 `secrets.randbelow` 在合法范围抽取；ECDSA 签名交给底层密码库，不自行选择或复用 nonce。私钥和真实身份不属于同步协议内容。
- `HASH160 = RIPEMD160(SHA256(pubkey))`。交易 ID、Merkle 内节点、教学区块头与内容校验使用双 SHA-256；Merkle 奇数叶复制末叶。项目显示原始内部字节序 HEX，不采用比特币区块浏览器常见的反向 TXID 显示。
- 创世状态预置 4 个教学 UTXO，每个金额 1000；每区块 4 笔单输入单输出交易，各扣除 1 单位手续费。验证未花费输入、禁止重复输入、金额非负与输出不超过输入。
- **区块容器和通信协议自定义**，不是比特币主网格式或 Bitcoin P2P 协议；未实现 PoW、挖矿、最长链选择、分叉处理、完整共识、币基奖励或真实网络地址发现。只支持旧式 P2PKH 与 SIGHASH_ALL，不支持 SegWit、Taproot 和完整脚本类型。
- 预置信任创世 UTXO 和目标链顶哈希。因此能检验“收到的数据与既定链一致”，不能解决“哪条链是真实链”。这不是公链，不据此声称抗女巫或抗拜占庭攻击。
- 每个区块固定 4 笔交易，通过双 SHA-256 承诺的**教学填充区**改变传输大小。因此区块大小实验主要研究传输和数据哈希成本，不能代表每 MiB 含大量真实交易时的验签成本。没有用随机填充冒充交易。
- 不加 TLS，绑定本机；未实现公网认证、流量防护、持久化恢复或生产级资源隔离。连接与输入有界，数据仅用于教学。密码库脚本验证不等同于 Bitcoin Core 的完整共识验证。

## 网络模型与公平比较

| 条件 | 注入方式 |
| --- | --- |
| 正常 | 每个控制或 GET 响应固定等待 2 ms；共享数据服务速率 16 MiB/s |
| 中断 | 节点 0 对每个区块第一次 GET 传输一半后强制断开 |
| 不响应 | 节点 0 接受 GET 后等待 2 s；客户端响应头超时 120 ms；HELLO 和 HEADERS 正常 |
| 请求过多 | 所有提供者起初 40 ms 返回 BUSY；每个提供者同时最多服务 2 个 GET |
| 拥塞条件 | 响应等待 15 ms；共享 FIFO 数据速率 2 MiB/s |

共享队列按 16 KiB 分块串行服务；每块先等待字节数/配置速率，再真实写入 TCP。排队时间及忙碌时间均在这段应用层资源上测量。操作系统实际 TCP 拥塞控制仍存在，但**本实验没有测量公网丢包率、TCP 拥塞窗口或路由器队列**。延迟值是每次响应前的固定等待，不应称为实测 RTT 或完整链路传播模型。HELLO 和 HEADERS 不消耗配置的数据瓶颈带宽。

顺序基线：一次下载一个区块；首次选节点 0，失败后轮换到同一 4 节点池；失败整块重传。优化方案：默认 4 路轮换多源，有失败节点短暂冷却，保留已接收前缀并经完整哈希认证后接受。两种方案都有超时、有限退避和重试。优化比较衡量这一组措施的组合效果，不能归因到单个措施；单独的“断点续传节省字节”测试提供局部证据。

主矩阵 3 大小 × 4 同步数量 × 5 条件 × 2 策略 × 3 次 = 360 次。发现比较为 2 延迟条件 × 2 并发度 × 3 次 = 12 次，目标都是验证 100 个活跃节点。附加负载实验为 4 个同时启动的同步会话，竞争同一容量为 2 的提供者，每会话 3 个 256 KiB 区块，比较并发度 1、2、4、8，共 24 次。

## 指标解释

- 同步总耗时：获取头部清单、下载、完整校验至完成，单调高精度时钟 `perf_counter` 计时；不含预先生成区块和节点发现。发现耗时单独记录。
- 下载耗时：含 HEADERS、下载重试及完整字节校验和；验证耗时：解析、Merkle、Script 与 UTXO 更新。
- 有效吞吐量：通过全部校验的区块字节 / 同步总耗时 / 2²⁰，单位 MiB/s。
- 传输效率：有效区块字节 / 客户端实际接收的区块数据字节，重传计入分母。控制帧、TCP/IP 头未计入，因此不是全链路协议效率。
- 排队 P95：每个数据分块等待共享 FIFO 资源的第 95 百分位；`queue_peak` 为等待者峰值，不包含正在服务者；单路时可为 0。
- 负载实验以整组完成的会话字节计算吞吐，单个会话失败明确保留；多会话共享指标只按整组统计。
- 原始记录含重试、超时、BUSY、断开、校验失败。哈希校验错误会丢弃整个前缀后换源。

## 本次实际运行的结果

交付数据包含 **360 次同步、12 次发现、24 次并发负载测量**，每组重复 3 次。360 次同步全部完成完整校验；18 项自动测试通过，日志见 `results/tests.log`。压力实验共启动 96 个同步会话，74 个完成，22 个因重试预算耗尽而失败；这些失败保留在 `load_raw.csv`，没有剔除。

| 对照场景 | 顺序基线均值 | 优化均值 | 含义 |
| --- | --- | --- | --- |
| 发现100个节点，正常响应等待 | 0.2855 s | 0.0521 s | 8路发现约加速5.48倍 |
| 发现100个节点，15 ms响应等待 | 1.7866 s | 0.2839 s | 并行可重叠等待 |
| 10个64 KiB区块，连接中断 | 0.2257 s | 0.0706 s | 多源与续传约加速3.20倍 |
| 10个1 MiB区块，共享速率2 MiB/s | 5.9502 s | 5.8361 s | 带宽主导，加速仅约1.02倍 |
| 10个1 MiB区块，请求过多 | 0.8952 s | 0.9035 s | 本组优化略慢，未隐藏反向结果 |

完整均值、样本标准差、效率和排队指标见 `results/*_summary.csv`。固定数量和大小后，响应等待较小、节点可用、没有故障时通常更快；小幅差异也受单机调度噪声影响。只做3次重复，不将微小差异视为统计显著。

负载实验正常条件下，每会话并发度从1提高到4，整组有效吞吐由约10.42下降到8.17 MiB/s，平均BUSY由23.3增至80次。带宽受限时，会话可能在资源释放前耗尽有限重试预算。并发度8在每会话只有3个区块时，与4具有相同的实际任务上限。**压力组耗时短也可能因为任务提前失败，必须结合完成率看，不能仅按秒数判优。**

结论：有界并行有助于节点发现和多区块等待重叠；续传和换源有助于故障恢复；带宽占满时并发收益很小，超过提供者容量还会增加拒绝和重试。根据BUSY率自适应限流是后续改进方向，本项目尚未实现自动调参，不把它作为已验证功能。
